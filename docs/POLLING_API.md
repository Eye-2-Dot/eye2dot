# 폴링·음성 API 규격과 펌웨어 1 시리얼 약속 (구현됨)

앱에서 "출력하기"를 누른 작업을 서버가 대기열에 넣어 두고,
펌웨어(ESP32)가 1초마다 "출력할 것 있나?" 물어 가져가는 방식.

```
앱 "출력하기"  ──POST /print──────────▶  서버 대기열
ESP32 (1초마다) ──GET /jobs/next────────▶  없음 / 작업 1개
ESP32 출력 끝   ──POST /jobs/{id}/done──▶  완료 기록
```

**구현됨**: 실제 서버 `server/main.py` (대기열은 `server/jobs.py`, 거울 변환은 `server/mirror.py`,
음성 번호는 `server/speech_store.py`).
`firmware1/tools/poll_test_server.py` 는 인터넷·Gemini 키 없이 시험하던 미니 서버다.
**거울 처리를 하지 않으므로** 점자 값은 실제 서버와 다르다.

| 장 | 내용 |
|---|---|
| 1~4 | 폴링 (출력 작업 주고받기) |
| 5~6 | 음성 받기 (`speech_id`, `GET /speech/{id}`, `GET /speech?text=` 대체 규칙) |
| 7 | 펌웨어 1 안의 두 칩(ESP32-CAM ↔ ATmega2560) 시리얼 프레임 |

---

## 기기 이름

| 모드 | 기기 |
|---|---|
| `label` | `fw1` (라벨 출력기) |
| `book`  | `fw2` (책 타각기) |

서버가 모드로 기기를 정한다. 앱은 기기 이름을 몰라도 된다.

## 1. `POST /print` — 앱이 호출

결과 화면에서 받은 값을 그대로 보낸다. 점역을 다시 하지 않는다.

```json
{"mode":"label", "text":"우유", "reason":"흰색 종이팩…", "braille":[13,41]}
```

성공: `{"ok":true, "job_id":"7cabc156cc10", "device":"fw1", "waiting":1}`

| error | HTTP | 조건 |
|---|---|---|
| `invalid_mode` | 400 | mode 가 label/book 이 아님 (빠지면 label) |
| `missing_braille` | 400 | braille 이 없거나 비었음 |
| `invalid_braille` | 400 | 모양이 틀림 (라벨은 1차원 배열, 책은 줄마다 칸이 하나 이상 있는 2차원 배열) 또는 칸 값이 0~63 정수가 아님 |

- 앱은 **원래 모양(거울 아님)** 그대로 보낸다. 서버가 대기열에는 그대로 두고, 기기에 줄 때 거울로 바꾼다.
- 펌웨어 1 작업이면 서버가 이때 음성을 **뒤에서** 만들기 시작한다 (앱은 기다리지 않는다).

## 2. `GET /jobs/next?device=fw1` — ESP32 가 1초마다 호출

할 일 없음 (가장 흔함):
```json
{"ok":true, "job":null}
```

작업 있음 (앱이 `[13,41]` 을 보냈을 때):
```json
{"ok":true, "job":{"id":"7cabc156cc10", "mode":"label", "text":"우유",
                   "reason":"흰색 종이팩…", "braille":[41,13], "cell_count":2,
                   "speech_id":"4710c121fe89", "mirrored":true}}
```

- 한 번에 **한 개만**, 들어온 순서대로 준다. 기기별(`fw1`, `fw2`)로 대기열이 따로다.
- 준 작업은 대기열에서 빼서 "진행 중"으로 옮긴다. **같은 작업을 두 번 주지 않는다.**
- **`braille` 은 거울 모양**이다 (`"mirrored": true`). 칸 안의 좌우 열만 바꾸고 칸·줄 순서는 그대로다.
  라벨은 1차원, 책은 2차원. 약속은 [`api-spec.md`](api-spec.md) "기기로 보내는 점자는 거울 모양".
- `cell_count` 는 전체 칸 수 (책은 모든 줄의 합).
- `id` 는 영문·숫자만 (주소에 그대로 들어가므로).
- 기기 이름이 없거나 틀리면 400 `invalid_device`.
- `speech_id` 는 **`fw1` 작업에만** 붙는다 (음성 안내는 펌웨어 1 전용). 있으면 ESP32 가 `GET /speech/{speech_id}` 로 음성을 받고,
  없으면 `text`·`reason` 으로 `GET /speech?text=` 를 부른다 (5·6장).
  대기열에서 10분 넘게 기다려 번호가 만료됐으면 줄 때 새 번호를 붙인다.
- 기기는 2초만 기다리므로 서버는 여기서 음성을 기다리지 않는다. 아직 만드는 중이면 `GET /speech/{speech_id}` 가 기다렸다가 준다.

## 3. `POST /jobs/{id}/done` — ESP32 가 출력 후 호출

```json
{"device":"fw1", "ok":true, "error":""}
```

실패했으면 `"ok":false` 와 아래 `error` 중 하나.

| error | 뜻 |
|---|---|
| `print_failed` | ATmega 가 실패('E': 타각 실패, 115초 동안 출력 버튼을 누르지 않음)를 보냈거나 130초 안에 답이 없음 |
| `bad_braille` | 점자 데이터가 비었거나 형식이 다름 |
| `cancelled` | 기기에서 촬영 버튼을 눌러(재촬영) 이 작업을 취소함 |

응답 `{"ok":true}`. 진행 중이 아닌 id 면 404 `unknown_job`.

## 4. `GET /jobs` — 확인용

대기 중·진행 중·최근 완료 작업을 보여 준다. 브라우저로 열어 확인.

```json
{"waiting":{"fw1":[], "fw2":[]},
 "in_progress":{"7cabc156cc10":{"device":"fw1", "seconds":3.2}},
 "history":[{"id":"…", "device":"fw2", "ok":false, "error":"cancelled", "seconds":0.2}]}
```

`history` 는 최근 20개.

---

## 정해 둔 것

- **완료 보고가 안 와도 자동으로 다시 주지 않는다.**
  책 한 쪽 타각은 몇 분 걸릴 수 있어서, 시간이 지났다고 다시 주면 같은 쪽이 두 번 찍힌다.
  필요하면 나중에 "다시 출력" 기능을 앱에 따로 둔다.
- 대기열은 메모리에만 둔다. 서버를 재시작하면 비워진다. 전시용으로는 충분하다.
- 기기 촬영 버튼 → 촬영 경로(`/process-file`. ESP32 의 `USE_MOCK` 이 true 면 `/process-mock`)는 폴링과 상관없다.
  ESP32 가 먼저 묻고 바로 답을 받으므로 폴링이 필요 없다.
- ESP32 는 **할 일이 없을 때만** 폴링한다. 촬영해서 서버에 보내는 동안(최대 110초)과
  작업을 ATmega 로 보내 답을 기다리는 동안(최대 130초)에는 폴링하지 않는다.
- 앱 작업을 출력하는 도중에 기기에서 촬영 버튼을 누르면 그 작업은 `cancelled` 로 보고하고 새로 촬영한다.
  다시 주지 않으므로, 필요하면 앱에서 다시 "출력하기".

## 앱 쪽에서 할 일

결과 화면 "출력하기" 버튼의 TODO 자리에 `POST /print` 호출을 넣는다.
성공하면 "출력 대기열에 넣었습니다" 정도를 보여 주면 된다.

## 5. 음성 받기 — 어느 주소를 부르나

펌웨어 1은 인식 결과를 소리로 읽어 준다. 음성은 서버가 만들고, ESP32 가 받아 ATmega 로 넘긴다.

| 경우 | ESP32 가 부르는 주소 |
|---|---|
| 응답(또는 job)에 `speech_id` 가 있음 | `GET /speech/{speech_id}` — 서버가 만든 문장. 성공은 `"{text}입니다. {reason}"`, 실패는 reason + 안내 문장(`다시 찍어 주세요.` / `잠시 후 다시 눌러 주세요.`, 나누는 기준은 [`api-spec.md`](api-spec.md) "기기용 응답") |
| `speech_id` 가 없음 (`device` 없이 보낸 요청, 서버가 음성을 만들지 못한 경우) | `GET /speech?text=…` — 문장 = `"{text}입니다. {reason}"` (예: `사과입니다. 빨간 껍질에 …`) |
| 서버가 실패로 답했는데 `speech_id` 가 없음 | 고정 문구 `"인식하지 못했어요. 다시 찍어 주세요"` |

`speech_id` 는 `device=fw1` 일 때만 붙는다 (음성 안내는 펌웨어 1 전용).

- `text`(이름)가 비어 있으면 "입니다" 를 붙이지 않고 `reason` 만 읽는다.
- 문장이 **200자**(글자 수, 서버 `/speech` 의 한도)를 넘으면 뒤를 자른다 (reason 부터 잘린다).
- 문장은 UTF-8 로 퍼센트 인코딩한다 (`우유` → `%EC%9A%B0%EC%9C%A0`, 공백 → `%20`).
  200자 한글이면 주소가 약 1.9KB 가 된다.
- 음성을 **연결 3초 + 서버 응답 25초 + 본문 5초(합쳐 약 33초)** 안에 다 못 받으면 음성 없이 진행한다 (점자는 그대로 출력).
  "{text}입니다. {reason}" 은 매번 다른 문장이라 서버 캐시가 잘 안 맞아, 서버가 음성을 만드는 데 오래 걸리면 가끔 음성이 빠질 수 있다.
- **512KB**(8kHz 기준 약 64초)를 넘으면 앞부분만 쓴다. 음성은 ESP32 의 PSRAM(추가 메모리 4MB)에 받는다.
- 서버에 닿지 못해 음성도 못 받으면 ATmega 가 실패음을 낸다 (7장 `0x05`).

## 6. `GET /speech/{speech_id}` · `GET /speech?text=` — 응답 형식

두 주소 모두 같은 형식이고, 둘 다 실제 서버(`server/main.py`)에 있다.
`GET /speech/{speech_id}` 의 보관 규칙(최대 32개, 만든 뒤 10분)과 없는 번호(404 `unknown_speech`)는
[`api-spec.md`](api-spec.md) 의 `GET /speech/{speech_id}` 절.

**음성 형식(8kHz·8비트·무음 128 등)과 헤더는 [`api-spec.md`](api-spec.md) 의 `GET /speech` 절이 기준이다.**
`GET /speech/{speech_id}` 도 그 절의 "오디오 형식"·"성공 응답"·"실패 응답"을 그대로 따른다.

- ESP32 는 `Content-Length` 만큼 받는다.
- 200 이 아니면 본문은 JSON 오류다 → 재생하지 않고 음성 없이 진행.

시험 서버(`poll_test_server.py`)는 내용과 상관없이 1초짜리 440Hz 사인파를 돌려준다. 없는 `speech_id` 면 404 `unknown_speech`.

## 7. 펌웨어 1 시리얼 프레임 (ESP32-CAM ↔ ATmega2560)

ATmega 는 JSON 을 다루지 않는다. ESP32 가 점자·음성을 작은 바이트 묶음(프레임)으로 바꿔 보내고,
ATmega 는 1바이트로 답하거나 촬영을 요청한다.
값의 정의는 `firmware1/common/protocol.h` 한 곳에 있다 (두 칩이 같은 파일을 쓴다).

배선: ESP32 GPIO15(TX) → Mega D19(RX1), Mega D18(TX1) → 전압 분배(1kΩ+2kΩ) → ESP32 GPIO14(RX), GND 공통. 115200bps 8N1.

### ESP32 → ATmega: 프레임

```
[0xAA][종류 1B][길이 2B little-endian][내용 0~256B][검사값 1B]
검사값 = 종류 ^ 길이 하위 ^ 길이 상위 ^ 내용 전체   (XOR)
```

| 종류 | 이름 | 내용 | ATmega 동작 |
|---|---|---|---|
| `0x01` | 점자 | `[줄 수 1B]` + 줄마다 `[칸 수 1B][칸 값…]`. 칸 값 = **서버가 거울로 바꾼 6비트 값 = 솔레노이드 비트** (bit0 = 위에서 볼 때 왼쪽 위 솔레노이드 1번 … bit5 = 6번). **줄 수 0** = 점자 없음(음성만) | 새 작업 → 안내 재생. 어느 상태에서든 지금 작업을 정리하고 갈아탄다 |
| `0x02` | 음성 시작 | `[전체 바이트 수 4B little-endian]` | 자리가 있으면 `'R'` |
| `0x03` | 음성 조각 | PCM 1~256바이트 | 자리가 있으면 `'R'` |
| `0x04` | 음성 끝 | 없음 | — |
| `0x05` | 알림음 | `[알림 종류 1B]` 1 = 네트워크, 2 = 카메라, 3 = 그 밖 | 응답 없음. 종류와 상관없이 **실패음**(300Hz 0.6초). 인식 중이었으면 대기로 |

- 점자 칸 값은 ESP32·ATmega 가 **뒤집지 않고 그대로** 솔레노이드에 쓴다. 거울로 바꾸는 일은 서버만 한다
  (`/jobs/next?device=fw1`, `/process-file?device=fw1`). 약속은 [`api-spec.md`](api-spec.md) "기기로 보내는 점자는 거울 모양".
- 기기 촬영 경로는 ESP32 가 `/process-file`(`USE_MOCK` 이면 `/process-mock`) 주소에 `&device=fw1` 을 붙여
  거울 값과 `speech_id` 를 받는다. 앱 작업(`/jobs/next`)도 거울이다.

### ATmega → ESP32: 1바이트

| 값 | 뜻 | 언제 |
|---|---|---|
| `'C'` | 촬영해 달라 | 대기 중 촬영 버튼(D31). 작업 중이면 `'E'` 바로 뒤에 (재촬영) |
| `'R'` | 다음 음성 조각 | 링 버퍼에 256B 이상 여유가 있을 때 |
| `'D'` | 출력 완료 | 출력 버튼(D32) → 타각 성공, 또는 점자 없는 작업의 재생 끝 |
| `'E'` | 실패·취소 | 재촬영, 타각 실패, 작업이 온 뒤 115초 동안 출력 버튼을 누르지 않음 |

### 촬영 순서 (기기 촬영 버튼)

```
ATmega                                        ESP32
대기 — 촬영 버튼 → 준비음
'C' ─────────────────────────────────────────▶ 촬영 → POST /process-file → 결과
인식 중 (버튼 무시)                              110초 안에 아래 둘 중 하나를 보낸다
     ◀──────────────────────────────────────── 점자 + 음성 → 아래 "한 작업의 순서"
     ◀──────────────────────────────────────── 알림음 (촬영·서버 실패) → 실패음 → 대기
115초 동안 아무것도 오지 않으면 → 실패음 → 대기
```

### 한 작업의 순서 (촬영 결과와 앱 작업이 같다)

```
ESP32                                         ATmega
점자 ───────────────────────────────────────▶ 새 작업 → 안내 재생
음성 시작 ──────────────────────────────────▶ 링 버퍼 비우기
          ◀─────────────────────────────────── 'R'
음성 조각 ──────────────────────────────────▶ 저장 (버퍼 절반이 차면 재생 시작)
          ◀─────────────────────────────────── 'R'    … 반복
음성 끝 (마지막 조각 바로 뒤) ───────────────▶ 남은 것 재생 → 출력 대기
          ◀─────────────────────────────────── 'D' (출력 버튼 → 타각 → 완료음)
                                               'E' (타각 실패·시간 초과 → 실패음)
                                               'E' 'C' (재촬영)
```

- 출력 버튼은 재생 중에 눌러도 음성을 바로 멈추고 타각한다.
- 점자가 없는 작업(줄 수 0, 실패 안내): 재생 중 출력 버튼은 무시한다(안내를 끊지 않게). 다 재생하면 버튼 없이 `'D'`.
- 재촬영: 안내 재생·출력 대기 중 촬영 버튼 → ATmega 는 음성을 멈추고 `'E'` 다음에 바로 `'C'` 를 보낸다.
  ESP32 는 `'E'` 뒤 50ms 안에 `'C'` 가 따라오거나 `'C'` 만 와도 지금 작업을 취소하고 새로 촬영한다
  (앱 작업이었으면 서버에 `cancelled` 로 보고).
- 음성 도중에 `'D'`/`'E'`/`'C'` 가 오면 ESP32 는 남은 조각을 보내지 않는다. 음성 끝 뒤의 `'R'` 은 무시한다.
- ESP32 는 `'D'`/`'E'` 를 최대 **130초** 기다린다 (ATmega 시간 초과 115초 직전에 출력 버튼을 눌러도 한 줄 타각이 끝날 때까지).
  ATmega 는 작업이 온 뒤 115초가 지나면 스스로 `'E'` + 실패음.
- 검사값이 틀리거나 길이가 이상한 프레임은 버린다. 조각이 깨지면 ATmega 가 0.2초 뒤 `'R'` 을 다시 보낸다
  (그 조각만큼 소리가 빠질 뿐 멈추지 않는다). 1초 동안 조각이 없으면 음성이 끝난 것으로 본다.
- ESP32 의 `ATMEGA_CONNECTED` 가 false(단독 시험)면 응답을 기다리지 않고 조각을 쉬지 않고 보낸다.
  이때는 ATmega 의 `'C'` 도 무시하므로, ESP32 USB 시리얼에서 `c` 를 보내 촬영한다.

### 책 모드 (펌웨어 2) 를 위한 제안 — 아직 구현하지 않음

라벨은 한 줄이라 점자 프레임이 작지만, 책 한 쪽(25줄 × 40칸)은 1KB 를 넘어 ATmega 의 버퍼(256B)에 한 번에 들어가지 않는다.
그때는 **줄마다 점자 프레임을 하나씩** 보내고, ATmega 가 한 줄을 다 찍으면 `'R'` 로 다음 줄을 요청하는 방식을 제안한다
(음성 조각과 같은 흐름 제어).
