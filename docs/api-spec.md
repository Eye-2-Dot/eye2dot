# Eye 2 Dot API 명세

서버: `server/main.py` · 기본 주소: `http://localhost:8000`

설치: `cd server && pip install -r requirements.txt`

실행: `cd server && uvicorn main:app --reload`

---

## 공통 사항

### 모드

| 값 | 의미 |
|---|---|
| `label` | 사물 사진 → 사물 이름 → 점자 라벨 |
| `book` | 책 페이지 사진 → OCR 본문 → 점역 |

### 점자 셀 표현

점자 셀 하나는 **6비트 정수(mask)** 하나다. 점 번호 n(1~6)이 비트 (n-1)에 대응한다.

```
1 · · 4      예) {1, 4} → 0b001001 = 9
2 · · 5
3 · · 6
```

- `0`은 **빈 칸(공백)** 을 뜻한다.
- 유니코드 점자로 보려면 `chr(0x2800 + mask)`.

### 기기로 보내는 점자는 거울 모양 (`mirror.py`)

앱으로 가는 `braille`·`braille_preview`는 위 그대로(읽는 면 기준)다. **기기(펌웨어 1·2)로 가는 것만** 서버가 거울로 바꾼다.

- 펌웨어 1·2 모두 솔레노이드가 종이·라벨을 **위에서 아래로** 찍는다. 점이 아랫면으로 나오므로 사람은 **좌우로 뒤집어** 읽는다.
- 기계는 줄의 첫 칸(배열 0번)을 위에서 볼 때 **오른쪽 끝**에 찍고 왼쪽으로 진행한다. 줄은 위에서 아래로. → 칸 순서·줄 순서는 그대로 둔다.
- 솔레노이드 번호는 위에서 볼 때 **왼쪽 위가 1번**. → 칸 안에서 좌우 열만 바꾼다 (점 1↔4, 2↔5, 3↔6).

```
mirrored = ((m & 0b000111) << 3) | ((m >> 3) & 0b000111)
예) [32, 35, 8, 39] ("사과") → [4, 28, 1, 60]
```

- 칸 순서·줄 순서는 바꾸지 않고, 빈 칸(`0`)으로 채우지도 않는다. 두 번 바꾸면 원래대로다.
- 펌웨어(ESP32·ATmega)는 받은 값을 뒤집지 않고 그대로 솔레노이드 비트로 쓴다 (bit0 = 위에서 볼 때 왼쪽 위 솔레노이드).
- 거울 값이 들어 있는 응답에는 `"mirrored": true`가 붙는다 (아래 "기기용 응답", `docs/POLLING_API.md`의 `/jobs/next`).
- 자체 시험: `cd server && python mirror.py`

### CORS

개발 단계라 모든 출처를 허용한다 (`allow_origins=["*"]`). 외부 배포 시 특정 도메인만 허용할 것.

브라우저에서 띄운 앱도 `/speech`의 `X-Audio-Duration` 헤더를 읽을 수 있도록 노출해 두었다 (`expose_headers`).

### 폴링 (앱 "출력하기" → 기기)

`POST /print`, `GET /jobs/next?device=`, `POST /jobs/{id}/done`, `GET /jobs`는 [`POLLING_API.md`](POLLING_API.md) 1~4장에 있다.
기기에 주는 작업도 아래 "기기용 응답"처럼 거울 점자 + (`fw1`만) `speech_id` + `"mirrored": true`다.

## `POST /process`

JPEG 바이트를 multipart 로 감싸지 않고 그대로 본문에 넣는 주소. `mode`는 쿼리로만 받는다.
**지금은 앱도 펌웨어도 쓰지 않는다** (앱 = `/process-file`, 펌웨어 1 = `/process-file` 또는 `/process-mock`).

```
POST /process?mode=label
Content-Type: image/jpeg

<JPEG 바이너리>
```

> **알려진 점**: 본문이 비어 있으면 400 이지만, 다른 오류와 달리 `{ok, error, reason}` 이 아니라 FastAPI 기본 형식 `{"detail": "이미지가 비어 있습니다"}` 로 답한다.

## `POST /process-file`

앱과 펌웨어 1이 쓰는 촬영 주소. `multipart/form-data`. 서버의 `/docs` 화면에서 파일을 올려 시험할 때도 쓴다.

| 필드 | 위치 | 필수 | 설명 |
|---|---|---|---|
| `mode` | 쿼리 또는 form | 아니오 (기본 `label`) | `label` 또는 `book`. **쿼리(`?mode=`)를 먼저 보고**, 없으면 form 필드, 둘 다 없으면 `label`. 빈 값(`?mode=`)은 없는 것으로 본다 |
| `image` | form (파일) | **예** | 이미지 파일 |
| `device` | 쿼리 | 아니오 | `fw1`(라벨, mode=label) 또는 `fw2`(책, mode=book). 붙이면 **기기용 응답**(아래 "기기용 응답"). 없거나 빈 값이면 지금까지와 똑같은 앱용 응답 |

앱은 쿼리로 보내고 (`POST /process-file?mode=label`), 펌웨어 1은 쿼리와 form 둘 다에 넣는다.
펌웨어 1은 `&device=fw1`을 붙여야 거울 점자와 `speech_id`를 받는다.

## `POST /process-mock`

**앱 개발용 목(mock).** Gemini를 호출하지 않고 고정된 더미 결과를 즉시 반환한다.
`GEMINI_API_KEY` 없이도, 카메라 없이도 앱 화면을 개발할 수 있다.

| 필드 | 위치 | 필수 | 설명 |
|---|---|---|---|
| `mode` | **쿼리** | 아니오 (기본 `label`) | `label` 또는 `book` |
| `image` | form (파일) | 아니오 | 붙여도 되고 안 붙여도 된다. 붙여도 읽지 않는다 |
| `device` | 쿼리 | 아니오 | `/process-file`과 같다 (`?device=fw1` → 기기용 응답) |

```
POST /process-mock?mode=book
```

응답 형식은 `/process-file`과 **완전히 동일**하다. 앱은 나중에 주소에서 `-mock`만 떼면 그대로 실서버로 전환된다.
`?mode=label&device=fw1`이면 Gemini 없이 기기용 응답(거울 점자 + `speech_id`)을 시험할 수 있다 (음성을 만들려면 서버에 인터넷이 필요하다).

## `POST /translate`

**사진 없이 텍스트만 점역한다** (앱의 "라벨 문구 직접 입력하기"용). Gemini를 부르지 않는다. `application/json`.

```
POST /translate
Content-Type: application/json

{"text": "우유", "mode": "label"}
```

| 필드 | 필수 | 설명 |
|---|---|---|
| `text` | **예** | 점역할 글. 앞뒤 공백만 뗀다 (책 본문 중간의 `\n`은 줄 나누기에 쓰이므로 그대로 둔다). **라벨 50자 / 책 2000자 이하** |
| `mode` | 아니오 (기본 `label`) | `label` 또는 `book` |

성공 응답은 아래 "성공 응답"과 같은 형식이고, `text`는 입력한 글, `reason`은 항상 `"직접 입력한 문구입니다."` 다.

실패는 모두 HTTP 400 + `{ok: false, error, reason}`:

| `error` | 발생 조건 |
|---|---|
| `invalid_mode` | `mode`가 `label`/`book`이 아님 |
| `missing_text` | `text`가 없거나 공백뿐, 또는 점자로 바꿀 글자가 없음 (문장부호만 있는 경우 등) |
| `text_too_long` | 라벨 50자 / 책 2000자 초과 |

## 성공 응답

네 엔드포인트(`/process`, `/process-file`, `/process-mock`, `/translate`)가 모두 같은 형식을 쓴다 (`device`를 붙이지 않았을 때. 붙였을 때는 아래 "기기용 응답").

| 키 | 타입 | 설명 |
|---|---|---|
| `ok` | bool | 항상 `true` |
| `text` | string | 인식된 텍스트. 앱은 화면 표시, 펌웨어 1은 음성 안내에 사용. `book`은 개행(`\n`)이 그대로 남아 있다 |
| `reason` | string | 판단 근거 1문장. 펌웨어 1이 음성으로 읽어준다. 앱은 표시하지 않아도 된다 |
| `braille` | **모드에 따라 다름** | 아래 참고 |
| `braille_preview` | string | 사람이 눈으로 확인하는 유니코드 점자. `book`은 줄바꿈으로 이어 붙인다 |
| `cell_count` | int | 전체 점자 셀 수 (`book`은 모든 줄의 합) |

### ⚠️ `braille`의 타입은 모드에 따라 다르다

| 모드 | 타입 | 이유 |
|---|---|---|
| `label` | `int[]` (1차원) | 사물 이름 한 개라 항상 한 줄 |
| `book` | `int[][]` (2차원, 줄 단위) | 본문이 길어 여러 줄이 되므로, 펌웨어가 줄바꿈 위치를 알아야 한다 |

### `label` 응답 예시

```json
{
  "ok": true,
  "text": "우유",
  "reason": "흰색 종이팩에 우유 표기가 있습니다.",
  "braille": [13, 41],
  "braille_preview": "⠍⠩",
  "cell_count": 2
}
```

### `book` 응답 예시

`/process-mock?mode=book`의 실제 응답이다 (`braille`은 지면상 앞 2줄만, 실제로는 18줄 448셀).

```json
{
  "ok": true,
  "text": "점자는 손끝으로 읽는 문자이다. 여섯 개의 점을 일정한 규칙에 따라 조합하여 글자를 ...",
  "reason": "OCR로 텍스트를 인식했습니다.",
  "braille": [
    [40, 14, 34, 40, 35, 9, 42, 18, 0, 32, 37, 18, 32, 8, 42, 38, 42, 16, 37, 0, 21, 2, 1, 9, 42, 18],
    [17, 13, 18, 40, 35, 21, 10, 35, 0, 49, 32, 14, 4, 0, 8, 23, 58, 0, 40, 14, 34, 42, 2]
  ],
  "braille_preview": "⠨⠎⠢⠨⠣⠉⠪⠒⠀⠠⠥⠒⠠⠈⠪⠦⠪⠐⠥⠀⠕⠂⠁⠉⠪⠒\n⠑⠍⠒⠨⠣⠕⠊⠣⠀⠱⠠⠎⠄⠀⠈⠗⠺⠀⠨⠎⠢⠪⠂",
  "cell_count": 448
}
```

### `book`의 줄 나누기 규칙

`braille.py`의 `text_to_braille_lines()`가 담당한다.

- 한 줄 최대 셀 수는 `MAX_CELLS_PER_LINE = 30`. **하드웨어 실측 후 조정할 값이다.**
- 원문의 개행(`\n`) 위치에서는 무조건 줄을 바꾼다.
- 그 안에서 30셀을 넘으면 **낱말 경계(공백)** 에서 줄을 바꾼다. 낱말 중간은 자르지 않는다.
- 낱말 하나가 30셀보다 길면 담을 방법이 없으므로 그때만 30셀 단위로 끊는다.
- 낱말 사이 공백은 빈 칸(`0`) 한 개. 줄 맨 앞과 맨 끝에는 `0`이 오지 않는다.
- 점역 결과가 비는 줄(빈 문단 등)은 만들지 않는다. `braille`에 빈 배열은 들어가지 않는다.

## 실패 응답

| 키 | 타입 | 설명 |
|---|---|---|
| `ok` | bool | 항상 `false` |
| `error` | string | 오류 코드 (아래 표) |
| `reason` | string | 사용자에게 보여줄 실패 이유 |

| `error` | HTTP | 발생 조건 |
|---|---|---|
| `invalid_mode` | 400 | `mode`가 `label`/`book`이 아님 |
| `invalid_image` | 400 | 이미지로 열 수 없는 데이터 |
| `recognition_failed` | 200 | 사물·텍스트를 찾지 못함 |
| `rate_limit` | 429 | Gemini 요청 한도 초과 |
| `network_error` | 502 | Gemini 서버 연결 실패 |
| `parse_failed` | 500 | Gemini 응답 해석 실패 |

```json
{
  "ok": false,
  "error": "invalid_mode",
  "reason": "mode는 ['book', 'label'] 중 하나여야 합니다 (받은 값: 'banana')"
}
```

`recognition_failed`만 HTTP 200으로 나간다. 따라서 앱은 **상태 코드가 아니라 `ok` 필드로 성공 여부를 판단해야 한다.**

## 기기용 응답 (`?device=fw1` / `?device=fw2`)

`/process-file`·`/process-mock`에 `device`를 붙이면 기기(펌웨어)가 쓰기 좋은 형태로 답한다. 앱용 응답과 다른 점만 적는다.

| 키 | 앱용 | 기기용 (성공) | 기기용 (실패) |
|---|---|---|---|
| `ok` | ✓ | `true` | `false` |
| `error` | 실패일 때 | — | ✓ (앱용과 같음) |
| `text` · `reason` | ✓ | ✓ (펌웨어 1은 `speech_id`가 없을 때 이것으로 음성 문장을 만든다) | `reason` ✓ |
| `braille` | 원래 모양 | **거울 모양** (라벨 1차원, 책 2차원 = 줄 구조 그대로) | — |
| `braille_preview` | ✓ | **없음** (기기는 읽지 않고, 거울인지 헷갈리므로) | — |
| `cell_count` | ✓ | ✓ (거울이어도 같다. 책은 모든 줄의 합) | — |
| `speech_id` | — | **`fw1`만**, 음성을 만들었을 때만 | **`fw1`만**, 실패 안내 음성을 만들었을 때만 |
| `mirrored` | — | `true` | — |

- HTTP 상태 코드는 앱용과 같다 (`recognition_failed` 200, `rate_limit` 429 …).
- `device`가 `fw1`/`fw2`가 아니거나 mode와 맞지 않으면(`fw1` = `label`, `fw2` = `book`) **400 `invalid_device`**. mode 자체가 잘못되면 `invalid_mode`가 먼저 나간다.
- **음성(`speech_id`)은 펌웨어 1 전용이다.** `fw2`에는 붙이지 않는다.
- 펌웨어 1의 음성은 **응답하기 전에 서버가 미리 만들어** 번호를 붙인다. 그래서 응답이 음성 생성 시간(보통 1~3초)만큼 늦어지는 대신, 기기는 `GET /speech/{speech_id}`로 바로 받는다. 음성을 만들지 못하면(인터넷 끊김 등) `speech_id`를 빼고 답하며, 그때 펌웨어 1은 `GET /speech?text=`로 직접 받는다.

**음성 문장**

| 경우 | 문장 |
|---|---|
| 성공 | `"{text}입니다. {reason}"` (text가 비면 reason만). 예: `우유입니다. 흰색 종이팩에 우유 표기가 있습니다.` |
| 실패 | `reason` + 안내 문장. reason이 비면 기본 문장(아래). 예: `올바른 이미지 파일이 아닙니다. 다시 찍어 주세요.` |

| 실패 `error` | 안내 문장 | reason이 비었을 때 |
|---|---|---|
| `recognition_failed`, `invalid_image` | ` 다시 찍어 주세요.` (사진을 다시 찍으면 나아질 수 있음) | `인식하지 못했습니다.` |
| `rate_limit`, `network_error`, `parse_failed`, 그 밖의 서버 오류 | ` 잠시 후 다시 눌러 주세요.` (서버·AI 쪽 문제) | `서버에서 문제가 생겼습니다.` |
| `invalid_mode`, `invalid_device` | 음성 없음 (기기 설정 오류라 다시 해도 같다) | — |
| (위 모든 경우) reason에 이미 **"다시"** 가 들어 있음 | **붙이지 않는다** (겹침 방지. 예: `rate_limit`의 "…잠시 후 다시 시도하세요.") | — |

- 문장은 200자(`GET /speech`의 한도)까지. 넘으면 성공은 뒤를 자르고, 실패는 reason을 잘라 안내 문장을 남긴다.

## `GET /speech`

**펌웨어 1 음성 안내용.** 텍스트를 음성으로 바꿔 **오디오 바이트 그대로** 돌려준다 (JSON이 아니다).
음성 생성과 변환은 서버가 전부 하고, 기기는 받은 바이트를 재생만 한다.

### 요청

| 필드 | 위치 | 필수 | 설명 |
|---|---|---|---|
| `text` | 쿼리 | **예** | 읽어줄 텍스트. 앞뒤 공백을 뗀 뒤 **200자 이하**. **UTF-8로 퍼센트 인코딩**할 것 |

```
GET /speech?text=%EC%9A%B0%EC%9C%A0
```

- `%EC%9A%B0%EC%9C%A0`은 "우유"다. 한글 한 글자는 UTF-8로 3바이트라서 인코딩하면 `%XX` 3개, 9글자가 된다. 200자면 URL이 약 1.8KB.
- 인코딩 규칙: 영문·숫자와 `- _ . ~`는 그대로, 나머지 바이트(공백 포함)는 `%XX`. 펌웨어 1의 구현은 `firmware1/cam/src/net.cpp`의 `urlEncode()`.
- 200자는 **글자 수** 기준이다 (UTF-8 바이트 수가 아니다). 한글 한 글자도 1자.
- 서버가 Microsoft 음성 서버(edge-tts)를 거쳐 음성을 만들므로 **서버에 인터넷이 연결되어 있어야 한다.**
- 한 번 만든 텍스트는 서버가 기억해 두었다가(최근 64개) 다음부터 바로 돌려준다.
- 처음 요청하는 텍스트는 음성을 만드느라 수 초가 걸릴 수 있다. 서버는 음성 생성에 최대 15초, 변환에 최대 10초까지 기다린다.
- **펌웨어 1은 요청부터 10초 안에 다 못 받으면 음성 없이 진행한다** (점자는 그대로 출력. `firmware1/cam/include/net.h`의 `SPEECH_TIMEOUT_MS`). 서버가 음성을 늦게 만들면 가끔 음성이 빠질 수 있다는 뜻이다. 음성을 꼭 받아야 하는 클라이언트라면 시간 초과를 30초 정도로 잡을 것.

### 성공 응답 (200)

```
HTTP/1.1 200 OK
content-type: application/octet-stream
content-length: 12000
x-audio-duration: 1.500

<raw PCM 12000바이트>
```

(숫자는 1.5초짜리 음성일 때의 예시)

| 헤더 | 설명 |
|---|---|
| `Content-Length` | 오디오 바이트 수. 수신·버퍼 관리는 **이 값을 기준으로** 한다 |
| `X-Audio-Duration` | 재생 시간(초). `Content-Length ÷ 8000`을 소수점 셋째 자리까지 반올림한 문자열 |

> 서버는 헤더 이름을 소문자(`x-audio-duration`)로 보낸다. HTTP 헤더 이름은 대소문자를 구분하지 않으므로, 헤더를 찾을 때 대소문자를 무시하고 비교할 것.

### 오디오 형식

**음성 형식은 이 표가 기준이다.** `GET /speech/{speech_id}`(아래)와 펌웨어도 이 표를 따른다.

| 항목 | 값 |
|---|---|
| 샘플레이트 | **8000 Hz** |
| 샘플 크기 | **8비트 unsigned** (0~255) |
| 채널 | **모노** |
| 헤더 | **없음.** WAV 헤더 없이 본문 첫 바이트부터 바로 샘플이다 |
| 무음 | **128** (0이 아니다) |
| 크기 | 1바이트 = 샘플 1개 = 1/8000초 → **1초 = 8000바이트** |

- 받은 바이트를 순서대로, 1/8000초마다 한 개씩 8비트 PWM 듀티 값으로 그대로 쓰면 된다. 부호 변환이나 디코딩은 필요 없다.
- 1.5초 음성이면 12,000바이트다. ATmega2560의 RAM(8KB)에는 **1초 분량도 다 들어가지 않으므로** 전부 받아두고 재생할 수 없다. 펌웨어 1은 아래 "펌웨어 1이 받아 재생하는 방법"처럼 받으면서 조금씩 재생한다.

### 실패 응답

> ⚠️ **`/process` 계열과 달리 성공 여부는 HTTP 상태 코드로 판단한다.**
> **상태 코드가 200일 때만 본문이 오디오다.** 그 외에는 본문을 재생하지 말 것 (JSON 글자가 잡음으로 나온다).

실패 본문은 `/process`와 같은 형식의 JSON이다.

```json
{ "ok": false, "error": "tts_unavailable", "reason": "음성 서버 응답 시간이 초과되었습니다." }
```

| `error` | HTTP | 발생 조건 | 기기 대응 |
|---|---|---|---|
| `missing_text` | 400 | `text`가 없거나 비었음. 글자·숫자 없이 공백·기호뿐인 경우도 포함 | 요청을 만드는 코드 확인. 재시도해도 결과가 같다 |
| `text_too_long` | 400 | 앞뒤 공백을 뗀 `text`가 200자 초과 | 텍스트를 줄여서 다시 요청 |
| `tts_unavailable` | 503 | 서버의 인터넷 끊김, 음성 서버 응답 없음·시간 초과·거부, 서버에 edge-tts 미설치 | 음성 없이 진행. 잠시 후 재시도 가능 |
| `conversion_failed` | 500 | 서버의 오디오 변환(ffmpeg) 실패 | 음성 없이 진행 |

기기가 서버에 아예 접속하지 못하면(기기 쪽 네트워크 문제) HTTP 응답 자체가 오지 않는다. 이 경우는 기기의 연결 오류로 처리한다.

## `GET /speech/{speech_id}`

**펌웨어 1 전용.** 서버가 미리 만들어 둔 음성을 번호로 받는다. 긴 문장을 주소에 실어 보내지 않아도 된다.

```
GET /speech/4710c121fe89
```

| 항목 | 내용 |
|---|---|
| 번호가 붙는 곳 | `/process-file`·`/process-mock?device=fw1` 응답, `/jobs/next?device=fw1` 작업 (`docs/POLLING_API.md`) |
| 번호 모양 | 영문 소문자(a~f)·숫자 12자 |
| 성공 응답 | `GET /speech`와 **똑같다** (raw PCM, `Content-Length`, `X-Audio-Duration`, 위 "오디오 형식") |
| 실패 응답 | `GET /speech`의 `tts_unavailable`(503)·`conversion_failed`(500)와 같다 |
| 없는 번호 | **404** `{"ok": false, "error": "unknown_speech", "reason": "…"}` — 잘못된 번호이거나 만료됨 |
| 보관 | 서버 메모리에 **최대 32개, 만든 뒤 10분**. 넘치면 오래된 것부터 지운다. 서버를 다시 켜면 비워진다. `GET /speech`의 텍스트 캐시(최근 64개)와는 별개다 |
| 아직 만드는 중 | `/print` 작업의 음성은 뒤에서 만든다. 그 사이에 요청하면 다 만들 때까지 **최대 25초** 기다렸다가 답한다 (그래도 안 되면 503 `tts_unavailable`) |

### 펌웨어 1이 받아 재생하는 방법 (ESP32-CAM → ATmega2560)

실제 구현은 펌웨어에 있다. 이 절은 흐름과 코드 위치만 적는다.

```
서버 ─HTTP─▶ ESP32-CAM ─시리얼 프레임(115200bps)─▶ ATmega2560 링 버퍼 1KB ─8kHz 인터럽트─▶ D11 PWM ─▶ RC 필터 ─▶ LM386 ─▶ 스피커
```

1. ESP32가 `GET /speech/{speech_id}`(번호가 있을 때) 또는 `GET /speech?text=`로 음성을 PSRAM(ESP32의 추가 메모리)에 다 받는다. 상태 코드가 200이 아니거나 10초 안에 다 못 받으면 음성 없이 진행한다.
2. ESP32가 음성을 최대 256바이트 조각으로 나눠 ATmega로 보낸다. ATmega는 링 버퍼(끝에 닿으면 처음으로 돌아가며 쓰는 저장 공간)에 자리가 생길 때마다 `'R'`로 다음 조각을 요청한다. 시리얼 전송(초당 약 11,520바이트)이 재생(초당 8000바이트)보다 빨라서 이렇게 속도를 맞춘다(흐름 제어).
3. 버퍼가 절반(512바이트 = 64ms) 차면 재생을 시작한다. 조금 모아 두고 시작해야 전송이 잠깐 늦어져도 끊기지 않는다.
4. 타이머 인터럽트가 1/8000초마다 한 바이트씩 꺼내 PWM 듀티(켜져 있는 시간의 비율)로 쓴다. 디코딩은 필요 없다.

| 타이머 | 쓰임 (Arduino Mega, 16MHz) |
|---|---|
| Timer1 | 8비트 Fast PWM, 16MHz ÷ 256 = **62.5kHz** 반송파(소리를 싣는 바탕 신호, 귀에 들리지 않는 높이). 출력은 **D11(OC1A)** |
| Timer2 | CTC 모드(정해진 값에 닿으면 0으로 돌아가며 인터럽트), 16MHz ÷ (8 × 250) = **정확히 8000Hz**마다 인터럽트 |
| Timer0 | `millis()`·`delay()`용. 건드리지 않는다 |

- Timer1·Timer2는 오디오 전용이라 `tone()`, D9~D12의 `analogWrite()`를 함께 쓸 수 없다. 전체 목록은 `pins.h` 맨 위.
- 재생하지 않을 때도 PWM을 끄지 않고 무음(128)으로 켜 둔다. 출력이 0V와 중간 전압 사이를 갑자기 오가면 "딱" 소리가 나기 때문이다.

| 코드 위치 | 내용 |
|---|---|
| `firmware1/mega/src/speech.cpp` | 타이머 설정, 링 버퍼, 8kHz 인터럽트, 소리 신호 표 |
| `firmware1/mega/include/speech.h` | 재생 함수 설명, 링 버퍼 크기(`SPEECH_STREAM_BUFFER`) |
| `firmware1/mega/include/pins.h` | 오디오 핀, 함께 쓸 수 없는 기능 목록 |
| `firmware1/cam/src/net.cpp` | URL 인코딩(`urlEncode`), `GET /speech` 받기 |
| `docs/POLLING_API.md` 7장 | 음성 프레임(`0x02`~`0x04`)과 `'R'` 흐름 제어 순서 |

#### 출력 회로

- PWM 핀으로 스피커를 직접 구동하지 말 것 (핀 허용 전류를 넘어 칩이 손상될 수 있다). **RC 저역통과 필터 → 커플링 커패시터 → LM386 앰프 모듈 → 스피커** 순서로 연결한다.

```
핀 11 ──[1kΩ]──┬──(+)[10µF](−)──▶ LM386 모듈 IN
               │
           [0.047µF]
               │
              GND           ※ Mega GND · 앰프 모듈 GND · 앰프 전원 GND는 모두 공통으로 연결
```

- **RC 필터**: 1kΩ 직렬, 0.047µF(47nF)는 저항 뒤에서 GND로. 차단 주파수 약 3.4kHz. 음성 대역(8kHz 샘플이 담을 수 있는 상한 4kHz)은 통과시키고 62.5kHz PWM 반송파는 걸러낸다.
- **10µF 커플링 커패시터**(직류는 막고 소리 성분만 통과시키는 부품): 필터 출력에는 무음일 때도 약 2.5V의 직류가 실려 있으므로 앰프 입력 전에 막는다. 전해 커패시터라면 **+극을 필터 쪽**(전압이 높은 쪽)으로 둔다.
- **LM386 모듈 볼륨은 최소에서 시작**해 조금씩 올린다. 필터 출력은 최대 약 5Vpp라 LM386 입력에 비해 크다.
