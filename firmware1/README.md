# 펌웨어 1 — 라벨 출력기 (ESP32-CAM + ATmega2560)

라벨 출력기 안에는 칩이 2개 있고, 각각 독립된 PlatformIO 프로젝트다.

| 칩 | 폴더 | 맡은 일 |
|---|---|---|
| **ESP32-CAM** | `cam/` | 카메라 촬영, Wi-Fi, 서버 통신 전부. 서버의 JSON·음성을 작은 바이트 묶음(프레임)으로 바꿔 ATmega 로 넘김 |
| **ATmega2560** (Arduino Mega) | `mega/` | 촬영·출력 버튼, 스피커(음성 재생·소리 신호), 솔레노이드·스텝 모터(타각). JSON 은 다루지 않음 |

작업이 들어오는 입구는 두 개, 뒷부분은 하나다.

1. **기기 촬영** — 촬영 버튼(D31) → Mega 가 ESP32 에 `'C'` → ESP32 촬영 → `/process-file?mode=label&device=fw1` 로 전송 (`USE_MOCK` 이 true 면 `/process-mock`) → 결과
2. **앱 출력** — 앱 "출력하기" → 서버 대기열 → ESP32 가 할 일이 없을 때 1초마다 `/jobs/next` 로 확인

공통: 점자·음성 → Mega 가 음성을 들려줌 → **출력 버튼(D32)** → 타각 → `'D'`

서버는 기기(`device=fw1`)에 **거울 모양 점자**(칸 안의 좌우를 바꾼 값)와 **음성 번호**(`speech_id`)를 준다.
펌웨어는 받은 점자를 뒤집지 않고 그대로 솔레노이드에 쓴다 (아래 "기구 방향").

> **`USE_MOCK` 기본값은 `true`** 다 (`cam/include/net.h`). 이때 ESP32 는 촬영해도 `/process-mock` 으로 보내
> 늘 같은 가짜 결과('우유')를 받는다 (Gemini 를 부르지 않음).
> **실제 Gemini 로 시험하려면 `false`** 로 바꿔 ESP32 를 다시 올린다. 서버의 `server/.env` 에 `GEMINI_API_KEY` 가 있어야 한다.

## 데이터 흐름

```
 서버 ──Wi-Fi(HTTP)──▶ ESP32-CAM ──UART(전선 3가닥)──▶ ATmega2560 ──▶ 스피커 / 솔레노이드
   ▲   /process-file/mock │  점자·음성을 프레임으로        │   'C' 촬영해 달라
   │   /jobs/next         │                                 │   'R' 다음 음성 조각
   │   /speech/{id}       ◀─────────────────────────────────┘   'D' 출력 완료 / 'E' 실패·취소
   └── /jobs/{id}/done ◀── 결과 보고 (앱 작업)
```

한 작업: 점자 읽기 → 음성 받기(`speech_id` 가 있으면 `GET /speech/{id}`, 없으면 `GET /speech?text=` 로 "{text}입니다. {reason}")
→ ATmega 로 점자·음성 → ATmega 가 음성을 들려줌 → **출력 버튼 = 타각 후 'D'** → (앱 작업이면) 서버에 완료 보고.
서버가 실패로 답하면 서버가 만든 안내 음성("…다시 찍어 주세요." 등)만 들려주고
(`speech_id` 가 없으면 고정 문구 "인식하지 못했어요. 다시 찍어 주세요"), 촬영 실패나 서버에 닿지 못하면 실패음.

## 버튼과 상태 (ATmega)

| 상태 | 촬영 버튼 D31 | 출력 버튼 D32 |
|---|---|---|
| **대기** | 촬영 (`'C'` + 준비음) → 인식 중 | 잘못 누름 소리 |
| **인식 중** | 무시 | 무시 |
| **안내 재생** | 음성 멈춤 → 재촬영 (`'E'` `'C'` + 준비음) | 음성 멈추고 바로 타각 (점자 없는 실패 안내 중에는 무시) |
| **출력 대기** | 재촬영 (`'E'` `'C'` + 준비음) | 타각 |
| **타각 중** | 무시 | 무시 |

- 인식 중 115초 동안 결과가 없거나, ESP32 가 실패(알림음 프레임)를 보내면 → 실패음 → 대기
- 안내 음성이 끝나면 → 출력 대기. 점자 없는 작업(실패 안내)은 음성이 끝나면 `'D'` → 대기
- 타각 성공 → `'D'` + 완료음 → 대기. 타각 실패 → `'E'` + 실패음 → 대기
- 작업이 온 뒤 115초 동안 출력 버튼을 누르지 않으면 → `'E'` + 실패음 → 대기
- 어느 상태에서든 새 점자 프레임(앱 작업 등)이 오면 지금 작업을 정리하고 그 작업의 안내 재생으로 바꾼다

자세한 상태 표는 `mega/include/job.h` 머리 주석.

### 소리 신호

값은 `mega/src/speech.cpp` 맨 위 표 한 곳에 있다.

| 소리 | 뜻 |
|---|---|
| 1000Hz 짧게 1번 | 준비·촬영 (촬영 버튼이 눌림) |
| 400Hz 짧게 2번 | 잘못 누름 |
| 300Hz 길게 1번 | 실패 (촬영·서버·타각 실패, 시간 초과) |
| 1500Hz 짧게 2번 | 타각 완료 |
| 400Hz 3번 | 배터리 부족 (아직 쓰는 곳 없음) |

## VS Code 에서 열기

PlatformIO 는 `platformio.ini` 가 있는 폴더(`firmware1/mega`, `firmware1/cam`)만 프로젝트로 인식한다.
저장소 루트만 열면 인식하지 못하고, 편집기가 `Arduino.h` 를 찾지 못해 탐색기에서 `firmware1` 이 빨간색으로 보인다 (빌드에는 영향 없음).

**작업공간 파일**(여러 폴더를 한 창에 묶는 VS Code 파일)을 각자 하나 만들면 저장소 전체와 두 칩을 한 창에서 다룰 수 있다.

1. 저장소 루트에 아래 내용을 `eye2dot.code-workspace` 처럼 저장한다 (이름은 자유, 확장자만 `.code-workspace`).
2. VS Code 에서 **파일 → 파일에서 작업 영역 열기**(File → Open Workspace from File) 로 연다.

```json
{
  "folders": [
    { "path": "." },
    { "path": "firmware1/mega" },
    { "path": "firmware1/cam" }
  ],
  "settings": {}
}
```

- 경로는 작업공간 파일이 있는 폴더 기준이다. 저장소 루트가 아닌 곳에 두면 경로를 그에 맞게 바꾼다.
- **작업공간 파일은 git 에 올리지 않는다.** 루트 `.gitignore` 의 `*.code-workspace` 가 걸러 준다 (사람마다 컴퓨터·여는 폴더가 달라서).
- 하단 바의 빌드·업로드 버튼은 PlatformIO 가 지금 고른 프로젝트(mega 또는 cam) 하나에만 적용된다. 누르기 전에 어느 쪽인지 확인하고,
  헷갈리면 터미널에서 그 폴더로 `cd` 한 뒤 `pio run` 을 쓴다.
- 작업공간 없이 `firmware1/mega` 나 `firmware1/cam` 폴더 하나만 열어도 된다.

## 기구 방향 (찍는 방향)

- **헤드(솔레노이드)는 위, 암다이(점을 받쳐 주는 홈 판)는 아래**에 있고, 솔레노이드가 라벨을 위에서 아래로 찍는다.
- 라벨은 **대지(떼어 내는 종이)가 위, 바깥면(붙였을 때 보이는 면)이 아래**로 지나간다.
  점은 아랫면(바깥면)으로 튀어나오므로 사람은 라벨을 **좌우로 뒤집어** 읽는다.
- **박리판**(대지에서 라벨을 떼어 내는 판)은 위로 꺾는다.
- **솔레노이드 1번(D22)은 위에서 볼 때 왼쪽 위**다. 1·2·3번이 왼쪽 열, 4·5·6번이 오른쪽 열(위→아래).
- 줄의 첫 칸(배열 0번)을 위에서 볼 때 **오른쪽 끝**에 찍고 **왼쪽으로** 진행한다 (헤드 이동은 스텝 모터 담당, `mega/include/punch.h` 머리 주석).
- 그래서 서버가 기기에 줄 때 **칸 안의 좌우만** 바꾼다(점 1↔4, 2↔5, 3↔6). 칸 순서는 그대로다.
  **펌웨어는 절대 뒤집지 않는다.** 약속 전체는 [`docs/api-spec.md`](../docs/api-spec.md) "기기로 보내는 점자는 거울 모양".

## 배선

| ESP32-CAM | | Arduino Mega | 비고 |
|---|---|---|---|
| GPIO15 (TX) | → | D19 (RX1) | 직결. ATmega 는 3.3V 를 HIGH 로 인식 |
| GPIO14 (RX) | ← 전압 분배 ← | D18 (TX1) | **5V 직결 금지 — ESP32 가 망가진다** |
| GND | — | GND | **반드시 공통** (없으면 통신이 안 됨) |

전압 분배 (Mega 5V → 약 3.3V):

```
Mega D18 ──[ 1kΩ ]──┬──▶ ESP32 GPIO14
                    │
                  [ 2kΩ ]
                    │
                   GND
```

- Mega 의 `Serial`(D0·D1)은 USB 업로드·시험용이라 ESP32 연결에 쓰지 않는다.
- ESP32-CAM 의 GPIO14·15 는 microSD 슬롯과 같은 핀이다 → **SD 카드를 꽂지 말 것.**
- 버튼: 한쪽은 Mega 핀, 다른 쪽은 GND (누르면 LOW, 내부 풀업 사용). 전원은 배터리 선의 물리 스위치.

| 버튼 | Mega 핀 |
|---|---|
| 촬영·재촬영 | D31 |
| 출력 | D32 |

나머지 핀(스피커 D11, 솔레노이드 D22~27, 스텝 모터, 리밋 스위치 등)은 `mega/include/pins.h`.

**솔레노이드 배선 주의**

- **D22~D27 각각 10kΩ 풀다운 저항 → GND 를 권장한다** (핀과 GND 사이에 저항 하나씩).
  Mega 가 리셋된 직후, 부트로더(업로드를 받는 시작 프로그램)가 도는 동안, 업로드 중에는 핀이 떠 있어서(High-Z)
  L298N 이 이를 HIGH 로 읽으면 솔레노이드가 켜진 채로 있을 수 있다. 코드는 `setup()` 맨 처음에 핀을 LOW 로 잡지만
  그 전 구간은 저항으로만 막을 수 있다.
- **업로드할 때는 배터리를 빼고 USB 만** 꽂는다 (업로드 중 솔레노이드에 전원이 가지 않게).

## 빌드·업로드

각 폴더(`firmware1/mega`, `firmware1/cam`)에서:

| 작업 | 명령 | VS Code 하단 바 |
|---|---|---|
| 빌드 | `pio run` | ✓ |
| 업로드 | `pio run -t upload` | → |
| 시리얼 모니터 | `pio device monitor` | 🔌 |

(`pio` 가 PATH 에 없으면 `~/.platformio/penv/Scripts/platformio.exe`)

**COM 포트** — 저장소에는 적지 않는다 (컴퓨터마다 다름).

- 보드를 **하나만** 꽂으면 PlatformIO 가 자동으로 찾는다.
- **둘 다** 꽂아서 다른 보드에 올라가거나 모니터가 엉뚱한 보드를 열면:
  그 폴더의 `upload_ports.example.ini` 를 `upload_ports.ini` 로 복사하고, `;` 를 지우고 번호를 적는다.
  (`upload_ports.ini` 는 커밋되지 않는다. 번호는 장치 관리자 → 포트, 또는 `pio device list`)
- **한 번만** 바꿔 올리려면 `pio run -t upload --upload-port COM5`

목 서버 ↔ 실제 AI 전환은 `cam/include/net.h` 의 `USE_MOCK` (기본값 true = 가짜 결과, 맨 위 안내 참고), 라벨 ↔ 책은 `DEVICE_MODE`.

## 시험 방법

### 1. ATmega 혼자 — USB 명령으로 소리 시험, 버튼 확인

`mega` 를 올리고 시리얼 모니터(115200)에서 한 글자를 보낸다.

| 명령 | 동작 |
|---|---|
| `0` | 정지 |
| `1` | 고정값 128 — 무음이어야 정상 |
| `2` | 고정값 200 — "툭" 소리가 나면 스피커 경로 정상 |
| `3` / `4` / `5` | 440 / 1000 / 220Hz 사인파 |
| `?` | 도움말 |

대기가 아닐 때(인식 중·작업 중)는 0~5 를 실행하지 않고 "작업 중" 이라고만 답한다.
2초마다 상태(재생, 작업 상태, 받은 프레임 수, 남은 RAM)가 찍힌다.

버튼만으로도 확인할 수 있다: 대기에서 **D32** → 잘못 누름 소리, **D31** → 준비음 후 "인식 중"
(ESP32 가 없으면 115초 뒤 실패음과 함께 대기로).

### 2. ESP32 혼자 — `ATMEGA_CONNECTED` 를 `false` 로 바꿔서

`cam/include/link.h` 의 `ATMEGA_CONNECTED` 는 기본값이 `true` 다.
**ESP32 만 따로 시험할 때(USB 의 `c` 명령으로 촬영)만 `false`** 로 바꾼다
(코드를 고치지 않으려면 `cam/platformio.ini` 의 `build_flags` 에 `-DATMEGA_CONNECTED=false` 한 줄).
`false` 면 ESP32 는 ATmega 로 프레임을 보내기만 하고 응답을 기다리지 않고 성공으로 처리한다.
**시험이 끝나면 `true` 로 되돌린다.**

- **촬영**: ESP32 시리얼 모니터에서 `c` 를 보낸다 (ATmega 의 촬영 버튼 대신).
  이 모드에서는 Serial2 로 들어오는 `'C'` 는 무시한다 (선이 없으면 잡음이 `'C'` 로 읽힐 수 있어서).
- 보낸 프레임의 종류·크기는 ESP32 시리얼 모니터에 찍힌다.
- 부팅 로그의 `PSRAM: 있음` 과, 음성을 받을 때의 `[음성] … PSRAM` 으로 음성 버퍼가 PSRAM 에 잡혔는지 확인한다.

### 3. 두 보드 연결 + 실제 서버 — 앱 작업·기기 촬영

1. 배선하고 두 보드를 올린다. `ATMEGA_CONNECTED` 는 기본값 **`true`** 그대로 둔다
   (2번 시험에서 `false` 로 바꿨다면 되돌릴 것. ESP32 부팅 로그에 지금 값이 찍힌다).
2. 실제 서버를 띄운다. `server/.env` 에 `GEMINI_API_KEY` 가 있어야 서버가 켜지고,
   음성을 만들려면 서버 컴퓨터에 **인터넷**이 연결되어 있어야 한다.

```bash
# 처음 한 번 (저장소 루트에서)
python -m venv .venv
source .venv/Scripts/activate
pip install -r server/requirements.txt

# 터미널 1 — 실제 서버
source .venv/Scripts/activate
cd server
uvicorn main:app --host 0.0.0.0 --port 8000

# 터미널 2 — 출력 작업 하나 넣기 (앱의 "출력하기"와 같은 요청. 원래 모양 점자를 보낸다)
curl -X POST http://127.0.0.1:8000/print -H "Content-Type: application/json" \
  -d "{\"mode\":\"label\",\"text\":\"우유\",\"reason\":\"흰색 종이팩에 우유 표기가 있습니다.\",\"braille\":[13,41]}"
```

3. 1초 안에 ESP32 가 작업을 가져가고(서버가 거울 값 `[41,13]` 과 `speech_id` 를 준다) → 스피커에서
   "우유입니다. …" → **출력 버튼(D32)** 을 누르면 Mega 시리얼에 칸 값·솔레노이드 번호가 찍히고 완료음 →
   터미널 1에 `[완료] … ok=True` 가 뜨면 성공. 상태는 브라우저로 `/jobs`.
4. 재촬영 취소 시험: 작업을 하나 더 넣고, 음성이 나오는 동안 **촬영 버튼(D31)** →
   터미널 1에 `ok=False cancelled`, ESP32 는 바로 촬영을 시작한다.
5. 기기 촬영: 대기에서 **촬영 버튼(D31)**. `USE_MOCK` 이 true(기본값)면 `/process-mock?device=fw1` 이
   늘 같은 가짜 결과('우유', 거울 값 `[41,13]`)를 준다.

서버가 음성을 만들지 못하면(인터넷 끊김 등) `speech_id` 없이 답하고, ESP32 는 `GET /speech?text=` 로 다시 받는다.

> ⚠️ `firmware1/tools/poll_test_server.py` 는 **거울 처리를 하지 않는다.** 그 서버로 타각하면 칸 안의 좌우가
> 반대로 찍힌다. 타각 시험은 반드시 실제 서버(`server/`)로 할 것. (포트 8000 이 같으니 둘 중 하나만 켤 것)

### 4. 첫 타각 시험 — 찍는 방향 확인

원래 모양 `[1, 63]`(왼쪽 칸 = 점1 하나, 오른쪽 칸 = 6점)을 넣는다.

```bash
curl -X POST http://127.0.0.1:8000/print -H "Content-Type: application/json" \
  -d "{\"mode\":\"label\",\"text\":\"시험\",\"reason\":\"방향 확인\",\"braille\":[1,63]}"
```

- 서버는 기기에 **`[8, 63]`** 을 준다 (ESP32 시리얼의 `[점자 1줄]` 숫자로 확인. 유니코드 점자는 거울 모양으로 보이는 게 정상).
- 출력 버튼으로 찍은 뒤 **라벨을 좌우로 뒤집어** 읽었을 때 **왼쪽 칸 왼쪽 위에 점 하나, 오른쪽 칸에 6점**이면 정상이다.
- 다르게 나오면 솔레노이드 배선 순서(D22 = 위에서 볼 때 왼쪽 위)부터 확인한다. 펌웨어에서 뒤집어 맞추지 말 것.

## 시리얼 약속

두 칩 사이의 약속은 두 곳에만 적는다.

- **값** (통신 속도, 프레임 종류 번호, 크기 한도, 시간 한도): [`common/protocol.h`](common/protocol.h).
  두 칩이 같은 파일을 쓰므로 **바꾸면 두 보드 모두 다시 올릴 것.**
- **모양과 순서** (프레임 구조, `'C'`·`'R'`·`'D'`·`'E'` 의 뜻, 촬영·작업 순서, 시간 초과 때 동작): [`docs/POLLING_API.md`](../docs/POLLING_API.md) 7장.

## 알려진 점

- **통신 속도**: 16MHz ATmega 는 115200bps 를 약 2% 오차로 만든다. 짧은 배선에서는 보통 문제없고,
  깨진 프레임은 검사값으로 버린다. **하드웨어 시험에서 통신 오류가 잦으면** (Mega 상태 출력의 "버림" 숫자가
  계속 늘면) `common/protocol.h` 의 `LINK_BAUD` 를 **250000**(ATmega 오차 0%)으로 바꾸고 두 보드를 다시 올릴 것.
- **음성 받기 시간**: 서버는 기기 촬영 결과의 음성을 답하기 **전에** 만들어 두고, 앱 작업의 음성은 `/print` 때부터
  뒤에서 만든다. ESP32 는 연결 3초 + 서버 응답 25초(서버의 최대 대기와 같음) + 본문 5초, 합쳐 약 33초 안에
  못 받으면 점자만 출력한다.
- **음성 길이**: 문장은 200자까지, 음성은 512KB(약 64초)까지. 음성이 길면 출력 버튼을 누를 수 있는 시간
  (작업이 온 뒤 115초)이 그만큼 줄어든다.
- **ESP32 단독 시험 뒤 `ATMEGA_CONNECTED` 를 false 로 둔 채 두 보드를 연결하면** 음성 조각이 쉬지 않고 쏟아져 소리가 깨지고,
  버튼 결과와 상관없이 성공으로 보고되며, 촬영 버튼(`'C'`)도 무시된다. ESP32 부팅 로그에 지금 값이 찍힌다.
- **ESP32 는 한 번에 한 가지만 한다**: 촬영해서 서버에 보내는 동안(최대 110초)이나 작업을 ATmega 로 보내
  답을 기다리는 동안(최대 130초)에는 폴링하지 않는다. 작업을 기다리는 동안 촬영 버튼을 누르면 그 작업을
  취소하고 새로 촬영한다. (시간 계산은 `common/protocol.h` 의 시간 규칙 주석)
- **ESP32 가 부팅하는 동안(Wi-Fi 연결 중) 누른 촬영 버튼은 버려진다** → Mega 는 115초 뒤 실패음을 내고 대기로 돌아간다.
- **앱 작업의 음성을 받는 중에 촬영 버튼을 누르면**, ESP32 가 음성을 다 받은 뒤에야 그 작업을 취소하고 촬영하므로
  결과가 그만큼(최대 약 33초) 늦는다. 아주 드물게 Mega 의 115초를 넘기면 실패음이 난 뒤 결과가 새 작업으로 도착한다.
- PC 에서 Mega 시리얼 모니터를 열면 Mega 가 리셋된다. 작업 도중이면 ESP32 는 최대 130초 기다리는데,
  리셋된 Mega 에서 촬영 버튼을 누르면 ESP32 가 그 작업을 취소하고 바로 촬영한다.
- 타각(`punchBraille`)은 끝날 때까지 loop 를 멈추는 함수라, "타각 중" 상태는 그 호출 동안만 있다.

## 자주 나는 문제

| 증상 | 해결 |
|---|---|
| `secrets.h` 관련 `#error` | 위 "처음 한 번" 2번 |
| ESP32 업로드 시 `Failed to connect` | MB 보드면 IO0 버튼 누른 채 업로드 시작, FTDI면 IO0–GND 연결 후 리셋 |
| ESP32 모니터를 열면 아무것도 안 나옴 | MB 보드의 RST 버튼 한 번 |
| `Brownout detector was triggered` | 전원 부족 — 5V 2A 이상 |
| `[폴링] 서버에 /jobs/next 가 없습니다` | 서버가 폴링이 들어가기 전의 옛 버전 → main 의 최신 `server/` 로 다시 켠다 |
| 찍힌 점이 좌우 반대로 나옴 | `poll_test_server.py` 로 시험했거나(거울 처리 없음) 솔레노이드 배선 순서가 다름 → 위 "시험 방법 4" |
| 업로드 포트를 못 찾음 / 다른 보드에 올라감 | 위 "COM 포트" — `upload_ports.ini` 또는 `--upload-port` |
| 소리가 안 남 (작업 중) | Mega 시리얼의 "프레임 정상/버림" 확인. 정상이 안 늘면 배선(TX↔RX 교차, GND 공통) |
| 촬영 버튼을 누르면 준비음 뒤 115초 지나 실패음만 남 | ESP32 가 부팅 중이었거나, `ATMEGA_CONNECTED` 가 false, 또는 D18 → 분압 → GPIO14 배선 |
| PlatformIO 가 프로젝트를 못 찾음 | 위 "VS Code 에서 열기"의 작업공간 파일로 열었는지, 또는 `firmware1/mega`·`firmware1/cam` 폴더를 직접 열었는지 |
| 탐색기에서 `firmware1` 이 빨간색, `Arduino.h` 를 열 수 없다는 오류 | 저장소 루트만 열어서 생기는 편집기 표시 (빌드와 무관). 위 "VS Code 에서 열기"대로 작업공간 파일로 연다 |
